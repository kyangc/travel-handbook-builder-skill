# Travel handbook builder

Turn source-backed facts into a private, editable handbook without inventing missing facts or choosing travel plans. The runtime stores typed operations; it does not browse, interpret prose, choose destinations, book, or publish.

## Use the public surface

Resolve resources from this skill directory, not the process working directory. In Kimi this is `${KIMI_SKILL_DIR}`; in another agent use the directory containing this file. Read [installation and invocation](README.md) when choosing between skill-local setup and a preconfigured external Python via `TRAVEL_HANDBOOK_PYTHON`.

For ordinary work, start with the short [default workflow](references/DEFAULT_WORKFLOW_GUIDE.md); its file-backed CLI path is the default. Read the [optional Python examples](references/PYTHON_OPTIONAL_GUIDE.md) only for programmatic state handling, and a topic guide only when current material needs it. The stable launchers are `scripts/travel-handbook` and `scripts/python`; `read_workspace(state)["capabilities"]` is the live inventory. Do not inspect runtime source, Schema, tests, or historical payloads to invent a protocol.

For a new handbook, use the existing public semantic request to create a complete state, then initialize a new managed directory **before first opening the webpage**. Read the [managed continuation guide](references/CLIENT_GUIDE.md) for `client context`, `client read`, `prepare-place`, `prepare-request`, and `commit`. Corrections, availability work, arrangement changes, and specialized authoring still use established professional methods and topic guides to construct requests; the managed client journals and submits those public requests without wrapping each method. Withdrawal or unlinking is not full deletion: only use a documented method for the exact intended effect. It cannot attach an already-served external canonical.

## Create

By default, use the file-backed CLI path in the default workflow: `create`, read its actual revision, author and keep one semantic request from the material, review `preview`, then `apply`, `check`, and `client init ROOT --state FULL_STATE` before first browser preview. Keep the initial receipt; do not auto-approve a preview or infer a starting revision. Start the managed browser preview for `ROOT` from the outset with `preview-service`; it serves `ROOT/private-handbook.json` without moving the canonical path. A Place needs only a name structurally; missing optional images, hours, duration advice, address, coordinates, price, hotel, flight, or ticket evidence does not block a first handbook. Omit unknown optional fields instead of sending `null` or traveler-facing placeholders.

Use the source material's explicit choices. For a readable handbook, normally enrich already selected destinations with a few relevant facts: start with supplied material, then bounded reliable public research where needed. Before composing Place content or its Visit, read [content collection](references/CONTENT_COLLECTION_GUIDE.md) for scope and fact placement. A name-only Place is a valid first version, not a claim that content work is complete; optional gaps can be filled after feedback. Research does not authorize selecting new destinations, hotels, flights, Places, daily themes, or routes.

Before the first managed map preview, run `scripts/preview-service maps-status ROOT`. If `asked=false` and `configured=false`, ask the user once whether to configure a Google Maps JavaScript API key. Continue handbook authoring while waiting; a decline or no answer means run `maps-skip ROOT` and show only the handbook's own points and lines without a basemap. Later, `maps-configure ROOT` reads the key from standard input without printing it; refresh the same preview URL to enable Google Maps. No Google key is supplied with the Skill, and the fallback is not an offline street map. Never put the key in a semantic request, canonical export, shell argument, log, or share link. See [installation and invocation](README.md) for private configuration and browser-key restrictions.

## Enrich

Resume from the current managed state. For a Place supplement or correction, use `client context ROOT --handle PLACE_HANDLE` even if the handle is known (or `--name PLACE_NAME` to resolve one): it returns the Place, related GuideNotes and Sources, and current revision. Context is Place-only and has no `--target`; read other objects with `client read ROOT --handle OBJECT_HANDLE`. `--day` needs a returned Day handle, not a date: first read `--type day` and follow pagination. Default read includes capabilities; after inspecting them, use `--omit-capabilities` to omit only repeated capability metadata while preserving full objects, related handles, revision and pagination. Media inventory uses `client read ROOT --type media`; see the [read-only media checklist](references/MEDIA_GUIDE.md#只读素材清单). Submit the narrowest supported patch; preserve every field outside the requested change, carrying unchanged subfields forward when replacing a composite value. Record adopted facts with their real source kind and preserve applicability, exceptions, uncertainty, and recheck conditions.

Use `prepare-place` only for a supported source-backed, non-overwriting Place supplement. For a correction or structured `unsupported`, follow the indicated professional guide, use current context/read handles and revision to construct the existing public request, and submit it with `client prepare-request`/`commit` in the same managed directory. A correction may also require updating affected current GuideNotes with `guide.note.update`; preserve still-valid text, sources, exact citations, and unrelated notes, or state the old text's historical applicability. Do not edit managed files or run ordinary `apply` against them; do not return to the stale initialization state.

For a user-chosen trip name, use `trip.update(set={"title": ...})` on the existing Trip. If an existing Task has a mistaken action, correct it in place with `task.amend(set={"action": ...})` using the model's enum. If a Task points to a retired ordinary transport Item replaced by a formal Journey, read the new Journey's current owning Item and use `task.amend(set={"targets": [...]})` explicitly. A done Task requires `task.reopen` first; preserve its old action, completion history, and the old Item. Do not guess that the new journey carries an old ticket or booking.

Place content and intrinsic opening rules belong to the Place. The visit date, planned time, and planned dwell come only from Day → active Item → Place; never copy them into Place content, availability, or notes. A missing optional detail remains unknown and does not trigger a full-trip rewrite.

When practical visit length or transfers matter, inspect selected Day Items and known lodging endpoints before researching gaps. Keep reusable `Place.content.duration_advice`, this visit's Item timing, and explicit Journey/Route movement separate; use the [content collection guide](references/CONTENT_COLLECTION_GUIDE.md) for a bounded follow-up. Do not derive travel time from gaps between activities or select an unconfirmed mode or route.

## Adjust

Use `client read` before changing an object. Reuse identity-preserving methods such as `plan.move`, `plan.withdraw`, and documented update methods; do not delete and recreate an object to simulate an edit. To refine an existing Visit into a Route for the same occurrence, use `route.bind_visit` via the [movement guide](references/MOVEMENT_GUIDE.md), not a second `route.compose` Item; a separate visit to the same Place remains valid. `client prepare-request` previews and journals the exact public request; review it, `client commit` its operation ID, then read back affected objects and inspect warnings. Load the matching arrangement, time, route, source-adoption, or recovery guide before a specialized change.

## View and deliver

For initial creation, run `check` before `client init`. Thereafter `client check ROOT` returns the current full check report with state/canonical revisions and publication status; `client status` reports publication and the stable path. A valid current report does not imply a stale canonical or webpage has refreshed. The client retains the complete state and later journal for continuation. `export_package(...)` returns an export report; the canonical handbook is `export_report["package"]`. CLI `export` writes only that canonical package for old self-managed work, not a managed update. Import only a canonical package, never the complete state or export report; package import cannot restore authoring-only handles, receipts, snapshots, or decisions.

The authoring `preview` is a write dry-run; managed `prepare-request`/`prepare-place` return that preview before commit. Browser preview is separate: use either runtime route in [installation and invocation](README.md), then for managed work run `scripts/preview-service start "/absolute/output/managed handbook" --port 0` and use its returned URL. This command returns only after identity and current canonical readiness checks, and keeps the service available after the caller exits; `status` and `stop` take the same ROOT. Repeated `start` preserves the URL, including after managed commit; refresh that page and never replace its canonical directly. For data-only verification, `GET /api/handbook` returns the canonical package; only explicitly referenced local images are available through `GET /api/media/<id>`. Canonical files are not served by filename. For standalone exports, `scripts/preview-handbook` remains a foreground terminal command. If a local image is outside the canonical directory, pass `--media-root` to the preview command. Service readiness and HTTP/API data do not prove the UI rendered: without a rendered-page check, deliver verified data and any available URL while saying page visibility was not visually verified, rather than claiming text or images are visible.

For an ordinary traveler, lead with the actual change, material sources, conditions and unknowns, a usable preview URL and resumption location, and the true visual-check boundary. Keep request/operation IDs, raw handles, and revision/check internals in the managed record by default; include them when technical audit or handoff needs them, without hiding warnings or decisions the traveler still owns.

## Safety kernel

- Existing-object writes use `{"handle": handle_string}` from a public read; same-batch aliases use `{"local": "alias"}`. Never substitute raw domain IDs.
- Set `expected_revision` from a current read. A successful replay requires the same `request_id` and byte-for-byte equivalent payload; a new ID is a new write. Keep the initial caller-owned semantic request; later managed operations preserve exact requests and retry by the same operation ID.
- Batches are atomic. On `AuthoringError` or a structured CLI error, keep the pre-call state, inspect `code`, `op_index`, `parameter`, and validation paths, then make a deliberate corrected request. Do not edit state or canonical JSON directly.
- Protect manual edits, completed execution, done Tasks, resolved Issues, and confirmed facts. Older material is not authority to overwrite them.
- Follow every page when completeness matters. `related_handles` contains direct relationships, not a complete dependency graph.

## Load specialized protocols only when needed

- New-handbook managed lifecycle, one source-backed Place supplement, or professional request transport: [managed continuation client](references/CLIENT_GUIDE.md).
- Programmatic creation or professional supplement only: [optional Python examples](references/PYTHON_OPTIONAL_GUIDE.md).
- Complete source text, exact citations, request journals, synthetic-source attribution, unidentified recommendations, missing endpoints, unconfirmed entrances, exchange-rate adoption, and shuttle classification: [source preservation and identity decisions](references/RECOMMENDATION_ROUTE_DECISION_GUIDE.md).
- Place/location, sourced GuideNotes, and opening rules: [locations](references/LOCATION_GUIDE.md), [GuideNotes](references/GUIDE_NOTE_GUIDE.md), and the matching opening-hours links in the [public guide index](references/README.md).
- Images/Media: [media guide](references/MEDIA_GUIDE.md). `media.image.add` and `client read media`/`client check` establish recorded metadata and uses, not visual display. Browser preview renders explicit Trip/Place usages; local files require a canonical-contained path or a configured media root and still need a rendered-page check.
- Dates, times, unassigned Items, moves, withdrawals, and execution replacement: [time](references/TIME_PLAN_GUIDE.md), [unassigned items](references/UNASSIGNED_ITEM_GUIDE.md), and [arrangement edits](references/ARRANGEMENT_EDIT_GUIDE.md).
- Movement, scheduled transport, owned vehicles, and paths: [movement](references/MOVEMENT_GUIDE.md) and [transport services](references/TRANSPORT_SERVICE_GUIDE.md).
- Lodging and hotel arrival: [stay guide](references/STAY_GUIDE.md). One first arrival per Stay uses `check_in`; later returns use `return`, without separate luggage-drop, registration, key-collection, or second check-in states. This is itinerary semantics, not supplier confirmation or guaranteed early room access.
- Actionable preparation Tasks, category/action choice, and checklist history: [Task preparation](references/TASK_PREPARATION_GUIDE.md).
- Later versions of the same source: [source adoption](references/SOURCE_ADOPTION_GUIDE.md) or the narrower [duration refresh](references/SOURCE_GUIDE.md). There is no general synchronization or graph patch.
- Other supported topics: load only the relevant guide from the [public guide index](references/README.md).

Before delivery, spot-check changed facts, their sources and conditions, and the untouched comparison surface. For maps, use `client read ROOT --report map-coverage` and follow every `pagination.next_cursor` to audit current Day/Place/Stop/Recommendation/AccessPoint/Path coverage; see the [report contract](references/MAP_COVERAGE_GUIDE.md) and [Agent-side location review](references/LOCATION_GUIDE.md). Keep diagnostic counts and gap lists in internal work feedback, not traveler GuideNotes or map copy, while preserving map attribution. Hidden diagnostics do not mean complete data, and non-entrance points are not precise navigation entrances. The report proves input projection only, not SDK rendering or network availability. `check.valid`, a successful export, and a readable webpage do not prove factual accuracy, source completeness, travel feasibility, booking status, or publication readiness.
